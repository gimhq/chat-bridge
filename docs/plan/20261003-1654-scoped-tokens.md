# 20261003-1654-scoped-tokens Scoped API tokens: limit a token to chosen contacts and chats

- **status**: completed
- **createdAt**: 2026-10-03 16:54
- **approvedAt**: 2026-10-03 17:05
- **relatedTask**: 20261003-1654-scoped-tokens

## Context

- Auth is one middleware, `bearerAuth` in `internal/server/server.go`, comparing against
  `server.token` in constant time. Every `/v1` route sits behind it; nothing downstream knows
  who is calling.
- `docs/api.md` §10 promises "tokens may be scoped to accounts (`config.token_accounts`)"; that
  was never built.
- Data is keyed by `(account_id, chat_id)`: `chats`, `messages`, `chat_members`; `media` rows
  point at a message through `message_seq`; `events` carry `account_id` and a JSON payload.
  Persons (`persons`, `person_links`) already group contacts across accounts.
- A precedent for payload-based event filtering exists: `store.EventFilter.Person` matches
  `sender.id`, `user_id`, `chat_id`, `from.id` with `json_extract`.
- Search (`store.SearchMessages`) filters by account and optionally one chat.
- The schema is at base version 1; `storage.md` §8 says later changes append migrations.
- The web UI signs in with `server.token` and stores it in local storage.

## Proposal

**Token model.** `server.token` stays the admin token. Additional tokens live in a new `tokens`
table (migration 2): `id`, `name`, `secret_hash` (SHA-256 of a 32-byte random secret; the
plaintext is returned once at creation), `scope` JSON, `created_at`, `last_used_at`.

**Scope** is an allowlist:

```json
{
  "persons":  ["per_01J…"],
  "contacts": [{"account_id": "wa-main", "user_id": "8613800000000@s.whatsapp.net"}],
  "chats":    [{"account_id": "wa-main", "chat_id": "120363012345678901@g.us"}]
}
```

It resolves, per request, to a set of allowed contacts (listed contacts plus the current links
of listed persons) and a set of allowed chats (the direct chats with those contacts plus the
listed chats). Groups are reachable only when listed as a chat.

**Endpoints** (admin only): `GET /v1/tokens`, `POST /v1/tokens {name, scope}` → 201 with `token`
shown once, `PATCH /v1/tokens/{id} {name?, scope?}`, `DELETE /v1/tokens/{id}`.
`GET /v1/tokens/self` works for any token and returns its name and scope.

**Enforcement for a scoped token:**

| Routes | Behavior |
|---|---|
| chats: list, get, read, typing, messages list, send | only allowed chats; others `404` |
| messages: get, edit, delete, react | the chat of the message must be allowed; else `404` |
| `messages/search` | results limited to allowed chats |
| contacts: list, get, `/chats`, `/messages` | only allowed contacts; views limited to allowed chats |
| persons: list, get, `/chats`, `/messages` | only listed persons, limited to allowed chats |
| media: get, meta, fetch | the message that owns the media must be in an allowed chat; upload allowed on an account that has an allowed chat |
| events, events/stream | only events whose chat or contact is allowed, plus `account.status` of accounts in scope |
| accounts: list, get | accounts in scope, without `config`, `device`, `stats` |
| everything else (account create, patch, delete, login, logout, reconnect, `self`, keys, requests, chat create and `resolve`, chat and contact `PATCH`, person writes, webhooks, tokens, `status`, `platforms`) | `403 forbidden` |

**Code shape.** The middleware resolves the bearer to a principal (admin, or a token with its
resolved scope) and puts it in the request context. Routes are split into an admin-only group
and a scoped group. The core gets one authorization helper used by the chat- and message-level
methods, and passes the allowlist to the store list functions (`ListChats`, `SearchMessages`,
`ListContacts`, `ListEvents`, the contact and person views) as an extra filter, so restriction
happens in SQL and pagination stays correct. A new error code `forbidden` (403) joins §2.1.

Tests are written first: a table of (route, in-scope, out-of-scope) cases in `internal/server`,
plus store tests for each filtered query.

## Risks

- An unguarded route is a data leak. Mitigation: the scoped group is an explicit allowlist of
  routes, so a route added later is admin-only by default, and a test walks every registered
  route with a scoped token.
- Event filtering by JSON payload must cover every event shape; an event type that carries a
  chat or user under a new key is dropped (the safe direction) until a matcher is added.
- Scope resolution runs on every request (person links change); the allowlist is expected to be
  small. A large allowlist makes the `IN` lists long.
- Migration 2 is the first migration after the base schema; a database opened by this build
  cannot be opened by an older binary.
- Webhooks stay admin-only, so a scoped consumer has to use long-poll or SSE.

## Scope

`internal/store` (migration, `tokens.go`, filters on five list queries), `internal/core`
(principal, authorization helper, token management), `internal/server` (middleware, route
groups, handlers), `internal/model`, `docs/api.md`, `docs/storage.md`, tests. Optional
follow-up: a Tokens section on the System page of the web UI.

## Alternatives

- Tokens in the config file instead of the database: no migration and no endpoints, but every
  change needs a restart and the UI cannot manage them.
- Scope by account only, as §10 originally said: much smaller, but does not limit contacts.
- Enforce only at the HTTP layer by post-filtering results: no store changes, but pagination
  breaks and search can leak through counts and cursors.

## Annotations

- Approved 2026-10-03 with the proposal's defaults: groups only when listed, no read-only switch, `chats/resolve` admin-only, no UI page in this change.
- `account.status` events reach a scoped token without `config`, `device` and `stats`; media that no message references (uploads, avatars) is hidden from scoped tokens.
